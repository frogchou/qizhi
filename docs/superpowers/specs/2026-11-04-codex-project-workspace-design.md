# 栖知 Codex 项目工作区设计

**状态：待用户批准**
**日期：2026-11-04**
**范围：Windows 首发版本的 Codex 工作模块**

## 1. 意图

将现有设计中的一次性 `CodexTask` 升级为可长期使用的“Codex 项目工作区”。用户围绕一项工作创建项目，把明确选择的本地文件和 RAGFlow 资料加入项目，在项目内建立多个可持续恢复的会话，并让 Codex 的本地文件操作默认只读取这些资料、只在独立工作目录中生成或修改文件。

这个模块面向所有需要基于资料完成复杂工作的职场人员，不把产品限定为代码开发工具。典型任务包括阅读资料、整理方案、比较文档、生成报告、制作数据处理脚本以及创建新的办公文件。

核心承诺：

1. 原始资料不被 Codex 修改。
2. 未加入项目的用户文件默认不可读。
3. Codex 生成物只落在该项目的独立工作区。
4. 项目、会话、资料清单和生成物在栖知重启后仍可恢复。
5. 用户始终能看见当前项目向 Codex 暴露了什么、Codex 正在做什么、产生了什么。

## 2. 已确认的产品决策

- 一个项目是长期容器，包含共享资料、共享生成物和多个会话。
- 项目中的所有会话默认共享同一套项目资料和生成物。
- 每个会话对应一个独立、可恢复的 Codex thread；一个会话包含多个连续轮次。
- 某一轮可以先把新资料加入项目再发送任务，但不建立隐藏的“仅本轮可见”副本，避免后续会话上下文不可解释。
- 本地资料以快照形式复制到项目只读区，不把原始绝对路径直接交给 Codex。
- RAGFlow 片段保存为带来源元数据的 Markdown 资料；可下载的原文件经用户选择后也可作为项目资料保存。
- 对支持抽取的 PDF、Office、文本等资料，项目同时保存原始快照和由栖知生成的可读 Markdown/文本派生快照；Codex 以派生快照作为主要阅读入口，原件用于追溯和必要的格式处理。
- 工作区与资料区分离。资料区只读，工作区可写；网络、MCP、Skills、插件和连接器沿用用户本机 Codex 的现有能力与审批机制。
- 使用 Windows 原生 Codex，不使用 WSL，不以云端 Codex 作为首发执行后端。
- 复用本机 Codex CLI 已缓存的登录状态；栖知不要求已登录用户再次登录，也不复制或保存 Codex 凭据。
- 用户的个人 Codex 项目不会被自动加入栖知项目；用户已有的 Codex MCP、Skills、插件、连接器和账号级配置正常可用。
- 首版由栖知保障常见 PDF、Office 和文本资料可被可靠读取，但不内置独立的 DOCX/XLSX/PPTX 生成引擎；Codex 能生成什么项目文件，栖知就收集、展示和导出什么文件。

## 3. 目标、非目标与反目标

### 3.1 目标

1. 用户能创建、重命名、归档和恢复 Codex 项目。
2. 用户能在项目内创建、重命名、切换和继续多个会话。
3. 用户能从“今日/过去”、本地搜索和 RAGFlow 检索结果中把资料加入项目。
4. 用户能在发送前检查本轮可见资料、可写目录、网络状态和任务要求。
5. Codex 的回答、计划、命令、文件变更、审批请求和错误以结构化事件流展示。
6. 用户能预览、打开、导出生成物，或把生成物上传到 RAGFlow。
7. 应用或 Codex 子进程异常退出后，项目和已完成会话仍可恢复。

### 3.2 首发非目标

- 不在首发版本接入云端 Codex 任务。
- 不向 Codex 暴露栖知的全盘 NTFS 索引，也不允许 Codex自行搜索整台电脑。
- 不把 Git 分支、提交、diff 等开发专用概念作为核心界面。
- 不支持多人协作、项目云同步或跨电脑同步。
- 不允许多个会话同时写同一项目工作区；首发按项目串行执行任务。
- 不自动将生成物上传知识库或覆盖用户原文件。
- 不承诺任意办公文件都能在栖知内预览；无法预览时仍可用系统程序打开。
- 不承诺 Codex 一定能生成某种特定办公文件格式，也不在首版为此打包额外 Office 生成工具链。

### 3.3 反目标

- 不能用一段提示词冒充文件系统权限控制。
- 不能把原始文件目录直接设为 Codex 工作目录。
- 不能因用户选择了一个文件而隐式放开其父目录或整个磁盘。
- 不能把 Codex 原始终端输出直接堆到普通用户界面。
- 不能绕过 Codex 自身的审批机制执行需要审批的操作，也不能写入项目工作区之外的目录。

## 4. 方案比较

### 4.1 Codex 接入方式

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 每轮调用 `codex exec` | 实现简单，适合一次性任务 | 会话恢复、审批、流式结构化事件和长期项目体验较弱 | 不采用 |
| 在前端或 Node 辅助进程中使用 Codex SDK | 有线程能力，封装程度较高 | 当前桌面端核心运行时是 Rust/Tauri，引入额外常驻运行时和跨进程层意义不大 | 不采用 |
| Rust 启动本地 `codex app-server` 并通过 stdio 使用协议 | 原生支持 thread/turn、恢复、审批、流式事件、取消和沙箱策略；与 Tauri 后端边界一致 | 协议适配和进程恢复工作更多 | **采用** |

选择 app-server 的原因是栖知要构建一个完整客户端，而非只自动执行一条命令。官方协议已经提供本设计需要的会话和安全原语，无需自行解析终端文本。

### 4.2 资料交付方式

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 直接把原文件路径传给 Codex | 不复制文件 | 容易扩大读取范围，原件可能被改动，删除或移动后会话不可复现 | 不采用 |
| 将选定资料复制为项目快照，并以受限只读根暴露 | 权限边界清晰，可复现，可校验哈希，原件安全 | 占用额外磁盘空间，需要刷新快照机制 | **采用** |
| 通过栖知 MCP 工具按需读取文件和知识库 | 不必复制，可动态检索 | 首发复杂度高，工具权限、引用一致性和离线恢复需要额外设计 | 后续增强 |

## 5. 信息架构与界面

`Codex 工作`采用项目工作台，不再沿用“一次任务提交页”。

```text
┌──────────────┬─────────────────────────────────┬──────────────────┐
│ 项目与会话     │ 当前会话                         │ 项目上下文          │
│              │                                 │                  │
│ ＋ 新建项目    │ 项目名 / 会话名 / 运行状态          │ [资料] [生成物]      │
│ 项目 A        │ ─────────────────────────────  │                  │
│  ├ 会话 1     │ 用户消息（右）                    │ 共享资料清单         │
│  └ 会话 2     │ Codex 回答（左）                  │ 来源与快照状态       │
│ 项目 B        │ 可折叠：计划、命令、文件变更、审批     │ 生成文件清单         │
│              │                                 │                  │
│ 归档项目       │ ─────────────────────────────  │ ＋ 添加资料          │
│              │ [引用资料]  输入任务……       [发送] │ [打开项目目录]       │
└──────────────┴─────────────────────────────────┴──────────────────┘
```

### 5.1 左栏：项目和会话

- 顶部提供“新建项目”和项目搜索。
- 项目按最近活动排序，可折叠显示会话。
- 项目菜单：重命名、打开项目目录、归档、删除。
- 默认是归档；删除必须二次确认，并明确是否连同生成文件一起移入回收站。
- 会话菜单：重命名、从此会话分支、归档。
- 当前有任务运行时显示明确状态；切换页面不会停止任务。

### 5.2 中栏：持续会话

- 用户消息靠右，Codex 回答靠左，与知识库问答的会话语言保持一致。
- 回答使用 Markdown 渲染；复制、编辑后重发、停止任务均为就近操作。
- “编辑后重发”只把文字放回输入框，不改写历史。
- 计划、推理摘要、命令、命令输出和文件变更作为可折叠的过程卡片展示。
- 审批请求必须显示动作、目标路径或网络目的、原因和影响范围。
- 输入框固定在底部；Enter 发送，Shift+Enter 换行，正确处理中文输入法组合状态。
- 支持停止当前轮次；停止后保留已有回答和生成物，并标明“已中断”。

### 5.3 右栏：项目上下文

- `资料`页签列出本地文件快照、RAGFlow 片段和RAGFlow 原文件。
- 每项显示名称、类型、原始来源、导入时间、大小、哈希/远端 ID 和快照状态。
- 支持预览、定位原文件、刷新快照、从项目移除。
- 移除资料只影响后续轮次；历史会话已经获得的信息无法撤回，界面必须说明这一点。
- `生成物`页签按最近变更列出文件，支持预览、系统打开、另存、上传知识库。
- 右栏顶部始终显示项目摘要：`项目资料 N 项 · 仅项目目录可写 · Codex 扩展能力已启用`，并可展开查看当前 MCP、Skills、插件及网络状态。

### 5.4 新建项目流程

1. 输入项目名称和可选目标说明。
2. 添加初始资料：本地文件、本地文件夹中的显式选中文件、RAGFlow 检索片段或文档。
3. 显示预计复制大小、无法读取的文件和重名处理结果。
4. 展示权限摘要后创建项目。
5. 自动创建第一个会话，但在用户发送第一条任务前不启动 Codex thread。

创建空项目也被允许，适合让 Codex 从零生成新文件。

## 6. 项目目录与数据模型

### 6.1 物理目录

项目文件位于栖知应用数据目录，而不是用户原始资料目录：

```text
Qizhi/
└─ codex-projects/
   └─ <project-id>/
      ├─ materials/              # 只读资料快照
      │  ├─ local/
      │  └─ ragflow/
      ├─ workspace/              # Codex 唯一可写工作区
      └─ previews/               # 栖知生成的预览缓存，不暴露给 Codex
```

项目名称不直接作为目录名，避免非法字符、重命名和路径注入问题。项目元数据、来源绝对路径、Codex thread 映射和审计状态保存在 SQLite，不放入 Codex 可读目录。

`materials`中的文件保持稳定的显示名称；重名时追加短来源标识。每个快照记录内容哈希。刷新资料时写入新版本并原子切换当前版本，不能原地修改 Codex 正在读取的文件。

资料刷新采用版本化快照，而不是覆盖旧内容。每个 turn 记录当时可见的 material version 集合；被历史 turn 引用的旧版本在项目存在期间保留，因此用户可以重新查看当时的资料。未被任何 turn 引用的旧版本可在用户确认的空间清理中删除。

### 6.2 领域对象

- `CodexProject`
  - `id`, `name`, `goal`, `rootPath`, `status`
  - `createdAt`, `updatedAt`, `lastOpenedAt`
- `CodexConversation`
  - `id`, `projectId`, `title`
  - `codexThreadId`, `codexSessionId`
  - `status`, `createdAt`, `updatedAt`, `archivedAt`
- `CodexTurnProjection`
  - `id`, `conversationId`, `codexTurnId`, `userText`
  - `status`, `startedAt`, `completedAt`, `errorSummary`
  - 记录该轮使用的 material version 清单
- `CodexMessage`
  - `id`, `turnId`, `role`, `markdown`, `status`, `createdAt`
  - 持久化用户在界面上看见的完整消息，确保 app-server 暂时不可用时仍可阅读历史
- `CodexProcessItem`
  - `id`, `turnId`, `codexItemId`, `kind`, `title`, `safeSummary`, `status`
  - 保存计划、命令、文件变更、审批等可见过程卡片的脱敏投影
- `CodexMaterial`
  - `id`, `projectId`, `kind`, `displayName`, `snapshotPath`
  - 本地来源引用或 RAGFlow dataset/document/chunk 标识
  - `currentVersionId`, `snapshotState`, `importedAt`
- `CodexMaterialVersion`
  - `id`, `materialId`, `originalSnapshotPath`, `derivedSnapshotPath`
  - `contentHash`, `size`, `mimeType`, `extractorVersion`, `createdAt`
- `CodexArtifact`
  - `id`, `projectId`, `relativePath`, `contentHash`, `size`, `mimeType`
  - `createdByConversationId`, `createdByTurnId`, `detectedAt`, `state`
- `CodexApprovalRecord`
  - `id`, `projectId`, `conversationId`, `turnId`, `itemId`
  - `actionType`, `targetSummary`, `decision`, `createdAt`

Codex thread 是继续模型上下文的权威记录；栖知同时持久化用户可见的完整消息和脱敏过程投影。这样即使 app-server 暂时不可用或 thread 丢失，用户仍能阅读历史，但不能在缺少原 thread 时假装延续原模型上下文。

## 7. Codex 运行时设计

### 7.1 受控运行环境

- 栖知检测 Windows 原生 `codex` 可执行文件及版本，不弹出命令行窗口。
- 栖知在与本机 Codex CLI 相同的用户环境和默认 `CODEX_HOME` 下启动 app-server，因此复用 CLI 已缓存的 ChatGPT/API Key 登录状态和自动刷新能力。
- 初始化后调用 `account/read` 检查实际认证状态；已登录时直接使用，不再发起登录流程。
- 若 Codex 已安装但未登录、登录过期或账号策略不满足要求，界面提示用户完成 `codex login`，随后可点击“重新检测”。
- 栖知不读取、复制、导出或自行保存 `auth.json` 等 Codex 凭据。
- 栖知不额外禁用个人 MCP、Skills、插件、应用连接器、动态工具、Web 搜索或网络能力，尽量保持与用户直接使用 Codex 一致的体验。
- 项目工作目录始终位于栖知项目中，因此不会自动加载用户其他项目目录中的 AGENTS.md 或项目配置；用户的账号级和全局 Codex 配置正常生效。
- Rust 后端启动一个受管理的 `codex app-server --stdio` 子进程，完成 `initialize` 握手并持续读取 JSONL 事件。
- 子进程崩溃时自动重启；未完成轮次标记为中断，已有项目和会话不丢失。

### 7.2 Thread 映射

- 新会话首次发送时调用 `thread/start`，并保存返回的 `thread.id` 与 `sessionId`。
- 后续轮次调用 `turn/start`。
- 应用重启或 app-server 重启后调用 `thread/resume`。
- “从此会话分支”使用 `thread/fork`，并创建新的本地 `CodexConversation`。
- 若远端 thread 记录丢失，保留本地历史投影，提示用户创建新会话，不静默丢弃历史。

### 7.3 沙箱与权限

每次 `thread/start`、`thread/resume` 和 `turn/start`都重新传入并校验项目边界：

```json
{
  "cwd": "<project>/workspace",
  "approvalPolicy": "on-request",
  "sandboxPolicy": {
    "type": "workspaceWrite",
    "writableRoots": ["<project>/workspace"],
    "readOnlyAccess": {
      "type": "restricted",
      "includePlatformDefaults": true,
      "readableRoots": ["<project>/materials"]
    },
    "networkAccess": true
  }
}
```

实现时以当前 app-server schema 为准，但以下约束不可放宽：

- 仅 `workspace` 可写。
- `materials`只读。
- 未选择的用户目录不属于可读根。
- 网络、MCP、Skills、插件、连接器和 Web 搜索不由栖知额外禁用，继续遵循 Codex 配置与审批规则。
- Codex 请求访问其他文件时，界面不提供“直接放开整个目录”；用户只能先将所需文件明确加入项目。
- 如果当前 Windows Codex 沙箱不支持受限读取根，功能必须失败关闭，并提示升级/修复 Codex，不能退化为全盘可读。

启动前调用 Windows sandbox readiness/capability 检查。安全摘要使用后端实际生效的策略生成，不接受前端自报状态。

这里的“只读取选定资料”特指 Codex 的本地文件系统操作。用户主动配置的 MCP、插件和连接器可能依据各自权限访问外部服务或其他数据；栖知不拦截这些能力，但必须在项目摘要中如实展示当前启用项，不能把扩展工具访问的数据错误标记成项目本地资料。

### 7.4 事件处理

Rust 适配器把 JSON-RPC 事件转换为稳定的栖知事件：

- thread/turn 生命周期
- agent message delta 与完成消息
- 计划和推理摘要（不展示模型私有原始推理）
- 命令开始、输出摘要和完成状态
- 文件变更与项目 diff 摘要
- 审批请求与处理结果
- 错误、用量限制和上下文压缩状态

所有事件包含 `projectId`、`conversationId`、`threadId`、`turnId`，防止多会话事件串线。完成事件是权威快照，前端不得重复追加增量文本。

## 8. 资料与生成物流程

### 8.1 加入本地资料

1. 用户在栖知文件列表、搜索结果或系统文件选择器中选择文件。
2. Rust 校验文件存在、大小、类型、访问权限和目标剩余空间。
3. UI 展示文件清单、来源和预计复制量。
4. 用户确认后复制到临时文件，计算哈希，再原子移动到 `materials/local`。
5. 对现有内容抽取层支持的格式生成 Markdown/文本派生快照，并记录抽取器版本；抽取失败时明确标记，不能假装 Codex 已能可靠阅读。
6. 保存来源映射，设置资料快照状态并刷新右栏。

文件夹不会作为隐式整目录授权。选择文件夹时先展开为明确文件清单，应用扫描排除与类型规则，用户确认后才导入。

### 8.2 加入 RAGFlow 资料

- 检索片段写成结构化 Markdown，包含标题、片段正文、dataset/document/chunk ID、相关度和检索时间。
- 同一 chunk ID 在项目内去重。
- 若用户选择完整文档且 RAGFlow 支持下载，下载后走与本地资料相同的快照和哈希流程。
- RAGFlow 连接失败不会影响已保存快照的离线使用。

### 8.3 刷新与移除资料

- 本地原文件变化时，资料显示“源文件已变化”，不会自动替换项目快照。
- 用户点击“刷新快照”并确认后才导入新版本。
- 新版本不会删除已被历史 turn 使用的旧快照；历史详情显示当时的版本和哈希。
- 移除资料会从未来轮次的可读根中删除该快照，但历史回答可能已经包含其信息。
- 正在运行任务时不允许刷新或移除资料，防止同一轮读取不一致。

### 8.4 生成物发现

- 优先使用 app-server 文件变更事件记录本轮生成物。
- 每轮完成后对 `workspace` 做受限增量核对，补齐未被事件捕获的新建/修改文件。
- 生成物只能使用项目内相对路径；符号链接、重解析点和路径穿越必须拒绝。
- 栖知不限制正常生成物的扩展名，也不对 Codex 的格式能力做额外承诺；凡是 Codex 在工作区内成功生成的文件，都作为项目生成物管理。
- Markdown、纯文本和常见代码/数据文件使用内置预览；其他格式优先交给系统默认程序打开。
- 导出使用系统保存对话框；上传知识库复用已有 RAGFlow 上传确认流程。

## 9. 状态、并发与恢复

### 9.1 项目状态

`active → archived → active`；删除是独立且需确认的终态操作。

### 9.2 会话状态

`draft → ready → running → ready`，异常分支为 `interrupted` 或 `unavailable`。一个会话同一时间只能有一个活动轮次。

### 9.3 并发规则

- 首发每个项目只允许一个运行中的轮次，避免多个会话同时修改共享工作区。
- 用户可浏览其他项目和会话，但向同一项目发送新任务时进入待发送状态或提示先停止当前任务。
- app-server 事件由 thread/turn ID 严格路由；页面切换或组件卸载不能取消后台任务。

### 9.4 恢复规则

- 栖知启动时先读取 SQLite 展示项目树，再异步检查 Codex 和 thread 状态。
- 上次状态为 `running` 但 app-server 没有活动轮次时，标记为“上次任务意外中断”。
- 已完成回答、资料和生成物不因 app-server 不可用而隐藏。
- 用户可以重试失败轮次，但重试会创建新 turn，不篡改旧记录。

## 10. 设置与诊断

设置页增加独立的“Codex”区域：

- Codex 可执行文件状态、版本和来源路径。
- 通过 `account/read` 获取的登录状态、认证类型和“重新检测”；未登录时提供清楚的 `codex login` 操作指引。
- Windows 沙箱状态与修复入口。
- 默认模型和推理强度（从 Codex 能力读取，不能硬编码不存在的模型）。
- 项目存储位置、已用空间和清理归档缓存。
- “测试 Codex”完成初始化、账号、扩展能力发现与项目文件边界自检，不读取项目之外的用户文件。

诊断信息必须区分：未安装、版本过旧、未登录、app-server 握手失败、Windows 沙箱未就绪、thread 无法恢复、权限策略不受支持。日志不得包含用户资料正文、API 凭据或完整提示内容。

## 11. 安全与隐私细节

- 所有项目路径由后端依据 project ID 解析；前端不能传入任意工作目录。
- 导入、刷新、预览、导出均检查规范化路径仍在对应根目录内。
- 拒绝符号链接、junction、重解析点逃逸和硬链接覆盖风险。
- 资料正文和会话正文不写入常规运行日志。
- 项目归档不改变文件权限；删除优先移入系统回收站。
- 生成物上传 RAGFlow 前必须显示文件、目标知识库和解析设置并由用户确认。
- 网络、MCP、Skills、插件和连接器继续使用 Codex 自身的配置与审批；栖知记录可见的审批结果，但不创建一套冲突的权限系统。

## 12. 首发实施范围

### 阶段 A：运行时与项目地基

- 数据库迁移与项目目录服务。
- Codex 检测、登录状态、app-server 生命周期和 Windows 沙箱能力检查。
- 项目/会话 CRUD 与 thread start/resume。
- 资料快照导入和目录边界测试。

### 阶段 B：可用工作台

- 三栏界面、项目树、会话历史、固定输入框。
- turn 流式事件、停止、错误和基础审批界面。
- 生成物发现、预览、打开和另存。

### 阶段 C：栖知资料联动

- 从今日/过去列表加入 Codex 项目。
- 从知识库检索结果加入片段或文档。
- 生成物上传 RAGFlow。
- 资料刷新、移除和来源状态。

阶段 A 和 B 构成首个可验收版本；阶段 C 完成原型中的本地资料与知识库联动闭环。

## 13. 验收标准

1. 创建两个项目后，它们的资料、会话和生成物完全隔离。
2. Codex 能连续完成至少三个轮次，重启栖知后恢复同一会话。
3. Codex 可以读取加入项目的资料，可以写入 `workspace`，但无法读取一个未加入项目的测试文件。
4. Codex 无法修改 `materials` 快照或写入项目外路径；失败不会触发隐式提权。
5. 网络、MCP、Skills 和插件保持可用，相关审批能够在栖知会话中正确展示和处理。
6. 从页面切换到今日、知识库或设置再返回时，任务、会话和选择不丢失。
7. app-server 强制结束后，栖知能报告中断、重新启动服务，并继续已完成会话。
8. 一个项目运行任务时，第二个会话不能并发写同一工作区。
9. 资料刷新前后均保留来源和哈希，可解释当前会话读取的是哪个快照。
10. 生成物可预览或打开、另存，并通过确认流程上传到指定知识库。
11. 自动化测试覆盖路径穿越、符号链接/重解析点、事件串线、增量重复、进程崩溃和 thread 丢失。

## 14. 实现者可决定的细节

- 三栏的精确宽度、收起断点、图标和动画。
- 项目名称自动建议与会话标题生成规则。
- 预览缓存格式和支持的首批文件类型。
- app-server 重启退避时间、流式事件批处理间隔和 UI 虚拟列表库。
- 生成物增量扫描实现，只要满足边界和验收标准。

这些实现选择不得改变已确认的项目共享模型、资料只读、工作区独立、Codex 扩展能力可用和多会话可恢复原则。
