# 真实多智能体编排中台设计

## 意图

把当前“一个需求固定调用一次 `knowledge.retrieve`”的演示路径替换为可扩展的企业中台：每个需求信号创建一个任务，中台用 Codex 根据已审核能力目录生成执行图，编译并验证该图，按依赖关系启动独立智能体实例，记录可恢复的过程、质量验收和交付物。首个端到端验收场景是“制作 438c 项目介绍 PPT”。

中台不是另一个万能智能体。它负责能力目录、规划、图编译、实例调度、状态机、恢复、审批、审计和用户可读的过程解释；业务工作由独立智能体完成。Codex 是规划智能体、PPT 智能体和质量智能体的运行时，不是绕过中台协议的后门。

## 当前审计结论

现有代码不能承担多智能体任务，具体原因如下：

1. `TaskService.createKnowledgeTask` 把任意目标写死成单个 `knowledge.retrieve` 节点，并在中台进程内直接导入、调用知识库智能体；未经过节点管理服务，也没有实例生命周期。
2. Codex CLI、`ppt-maker` 和 `quality-management` 已存在，但任务入口从不调用它们；因此当前时间线不代表真实编排。
3. 节点管理服务的能力目录只是进程内空 `Map`，未和中台的已审核版本同步；它没有可信的启动命令目录，重启后也会丢失。
4. 智能体只有事件回调，没有“结果回传”接口。各智能体把结果写入文件，但中台不知道何时、如何验证和接收该结果。
5. `MG_ENV_FILE` 仅被传给 systemd 单元为一个环境变量，智能体没有加载该文件；独立实例无法可靠获得 RAGFlow 凭据、回调地址或任务信封路径。
6. 数据库只有基础表，没有通用调度状态机、可运行节点选择、依赖完成判断、心跳续租、失败重试、取消或恢复流程。
7. 任务目录目前只被创建，没有稳定目录结构、会话记录、状态快照、计划版本、节点输入输出或可长期积累的记忆位置。
8. 协议只记录宽泛的 JSON 事件；控制台直接呈现 JSON，不能回答“为什么执行这一步、正在等什么、是否偏离预期”。
9. Codex 调用器缺少规划结果模式、超时/取消、运行日志归档和规划版本记录；中台无法审计规划依据。

这些问题必须优先解决；不在现有单节点方法上继续追加特例。

## 已选择的实现方式

采用“Codex 规划器 + 受控执行器”。替代方式是固定 PPT 流程，或由单个 Codex 进程自行完成全部工作；前者不具备通用性，后者绕开注册、审计、恢复和验收，因此不采用。

## 任务目录：任务的本地事实载体

每个需求创建唯一目录：

```text
/home/middleground/data/workspaces/<task-id>/
  task.json                         # 原始需求、提交人、验收模式、创建时间
  state.json                        # 可原子替换的任务状态快照与当前计划版本
  session/
    conversation.jsonl              # 中台规划、人工审批、系统决定的会话记录
    memory.md                       # 后续可扩展的任务记忆；首期仅保留位置和元数据
  plans/
    plan-v1.json                    # Codex 原始规划输出
    compiled-plan-v1.json           # 通过能力/图/输入校验后的执行图
    planner-summary.md              # 面向用户的中文意图、范围、理由与风险
  nodes/<node-key>/
    envelope.json                   # 该次实例的只读任务信封
    input.json                      # 经依赖产物解析后的节点输入
    result.json                     # 由智能体回传、经中台校验后的标准结果
    events.jsonl                    # 该节点的原始有序事件镜像
    runtime/                         # Codex 日志、渲染中间文件等
  artifacts/                         # 经 SHA-256 登记的最终或共享产物
  quality/                           # 验收标准、质量结论与重试意见
```

所有智能体以任务根目录为共同工作边界；每个节点只能在 `nodes/<node-key>` 写临时文件，跨节点共享必须显式使用 `artifacts/` 或在计划中声明 `sharingGroup`。数据库保存事务性状态、索引和审计；目录保存任务可移植的执行事实、会话和未来记忆。每次状态转换同时更新数据库和目录快照，恢复时以已确认的节点结果和检查点为准。

## 能力注册与运行时目录

智能体包在未审核阶段仍只读取 `agent.yaml`、输入/结果 JSON Schema 和声明的启动命令，登记为 `pending_review`。审核并完成自检后，中台发布一份只含 `ready` 版本的能力目录给节点管理服务；节点管理服务持久化该目录并在重启后恢复，拒绝未登记或非就绪版本。

能力目录每项至少包含：`agentId`、`version`、`capability`、中文名称/说明、`runtime`、经审核的 `entryCommand`、输入 Schema、结果 Schema、包路径和启动环境需求。规划器只看到这份目录，不能虚构能力；编译器以目录和 JSON Schema 校验计划并补全已选版本。

运行时由智能体包声明并被中台记录：

- `ragflow-knowledge`、`web-research`：`native`；在需要时可由自身调用 Codex，但不被强制。
- `ppt-maker`、`quality-management`：`codex`；每次实例通过受控 `CodexCliRunner` 调用本机已登录 Codex CLI。
- 中台规划器：`codex`；只生成结构化计划和中文规划说明，不直接生成交付物。

## 通讯规则

### 中台到节点管理服务

中台用内部令牌调用：能力目录同步、实例启动、停止和恢复。启动请求包含受审核版本、实例 ID、任务根目录、节点目录、环境文件路径和任务信封路径。节点管理服务只根据已同步目录构建命令，以 transient systemd 单元启动独立服务；不接受调用方任意给出的 shell 命令。

每个实例使用仅含该任务必要配置的 `EnvironmentFile`，由 systemd 以 `EnvironmentFile=` 载入。环境文件权限为 `0600`，不进入任务目录的会话、事件、结果或前端响应。

### 中台到智能体

中台把符合 Agent Protocol 的 `envelope.json` 写入节点目录，并提供：任务/节点/实例 ID、租约令牌、尝试次数、任务根目录、节点工作目录、显式共享组、输入、事件回调 URL、结果回调 URL、截止时间和恢复检查点引用。智能体不得猜测其他节点目录或凭据位置。

### 智能体到中台

保留有序事件回调，并新增结果回传：

- `started`、`progress`、`checkpoint`、`heartbeat`、`completed`、`failed` 事件都带租约令牌、序列号、中文 `message`、机器可读 `detail`、可选进度百分比和时间。
- `POST /internal/v1/instances/:instanceId/result` 接收符合 `AgentResultSchema` 的标准结果；中台验证租约、节点、路径、SHA-256 和结果 Schema 后才把节点置为完成。
- 节点完成事件不是成功依据；已校验的结果回传才是成功依据。

回调失败或重复事件保持幂等。心跳续租；租约过期、单元退出或中台重启会形成 `interrupted` 状态，而不是伪造完成。

## 规划、编译与执行状态机

任务状态为：`received → planning → plan_validating → queued → running → quality_review → awaiting_approval | accepted | failed | cancelled | interrupted`。节点状态为：`pending → ready → leasing → running → succeeded | failed | blocked | retrying | interrupted | skipped`。

1. 创建任务目录、任务记录和“收到需求”事件。
2. 中台读取当前 ready 能力目录，调用 Codex 规划器。其受模式约束的输出包括：中文意图说明、交付物、假设/风险、`TaskPlan`、每个节点的理由、验收要求和是否需要人工审批。
3. 编译器验证能力存在、节点输入符合该能力 Schema、依赖无环、共享目录显式声明、产物引用只在任务根目录内。失败时把规划问题交给规划器修正一次；仍失败则进入人工可见的 `failed`，不启动任何智能体。
4. 调度器按依赖选取 `ready` 节点，创建尝试、信封、环境文件和 transient 实例；绝不在中台进程内导入智能体的 `runTask`。
5. 调度器等待已验证的结果回传。后续节点从经登记的前序结果/产物得到输入，而非从任意目录读取。
6. 质量节点产出标准、检查结果和中文结论。失败时，中台可按用户已经同意的规则，依据质量意见自动安排一次明确的返工节点；第二次失败转人工审批。
7. 所有交付物通过 SHA-256、路径约束和质量结论后，进入自动验收或人工验收；任务目录和数据库留下可复盘会话。

### 438c PPT 的预期执行图

这不是写死模板，而是该需求在当前能力目录下应产生的可验证计划形态：多条 `knowledge.retrieve` 节点分别检索“438c 项目概述”“438c 项目时间/里程碑”“438c 项目成果/客户/团队”等，汇总为带出处的资料包；`presentation.create` 使用资料包生成 `presentation.pptx`；`quality.define_and_verify` 基于原始需求检查 PPT、资料追溯和可读性；若质量不通过，可由规划器生成一次受限返工。若知识不足，规划器可以选择 `research.web`，并在说明中标注外部资料来源和风险。

## 恢复、会话与记忆

调度器启动时扫描 `leasing`/`running` 尝试：有心跳且单元仍在运行的继续观察；租约过期或单元消失的标为 `interrupted`。若节点不存在已确认结果，则从最后一个 `checkpoint` 以新的实例和尝试次数恢复；已经确认结果的节点永不重复执行。恢复和重试均写入 `session/conversation.jsonl`、审计事件、数据库检查点和 `state.json`。

首期不实现跨任务个人长期记忆；`session/memory.md` 和元数据接口作为明确挂载点，避免把未来记忆混入审计日志或数据库字段。

## 控制台要求

控制台的默认视图必须是中文过程说明，不是原始 JSON：

- 顶部显示任务目标、当前状态、已用时间、阻塞/等待原因、验收模式和最终交付物。
- 中间显示真实执行图和节点依赖；每个节点展示“为什么执行”“使用哪个智能体/运行时”“输入摘要”“实时进度”“产物/证据”“耗时”“结果/风险”。
- 规划阶段展示 Codex 生成的意图、所见能力、计划理由、假设和风险；不能把模型内部思维链展示给用户。
- 右侧提供“开发调试”折叠区，才显示结构化 JSON、事件序列、实例 ID、租约、日志路径和原始回调。
- 审批页面展示质量结论、返工意见和待确认交付物；任务结果页提供受控的产物下载链接。

## 范围与非目标

本次实现必须交付一条真实的“438c 项目介绍 PPT”链路，以及可供未来能力复用的规划、编译、调度、回传、恢复和界面模型。

本次不实现：跨服务器节点、隔离的多租户权限、任意第三方运行时插件市场、跨任务长期记忆语义、自动发布到外部沟通系统。服务器仍按已确认条件以当前 root 账户运行，但协议和目录边界不能因此省略。

## 验收标准

1. 提交 438c PPT 需求后，控制台显示 Codex 规划出的真实能力目录和多节点执行图，而不是固定单检索节点。
2. 检索、PPT 和质量节点以独立 systemd 实例运行；中台日志不出现直接导入智能体执行代码的路径。
3. PPT 与质量节点的实例记录能证明本机 Codex CLI 被调用；规划节点也记录受模式约束的 Codex 结果摘要。
4. 每个任务目录包含计划、会话、节点信封/事件/结果、产物和状态快照；敏感环境变量不写入其中。
5. 中断后重启中台能恢复未确认节点，不重做有结果的节点；质量不通过最多自动返工一次。
6. 控制台以中文显示原因、进度、状态、耗时、交付物和验收，而 JSON 仅在调试区显示。
7. 覆盖协议、规划编译、目录边界、调度状态机、结果回传、恢复与 438c 端到端流程的自动化测试，并在 219 完成真实部署测试。
