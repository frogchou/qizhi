# 企业智能体中台与智能体群：第一期设计

**状态：待批准**<br>
**日期：2026-11-10**<br>
**部署目标：219 服务器（Ubuntu 26，`root@middleground.example.invalid`）**

## 1. 意图

本项目建设企业原生 AI 组织的底座，而非个人对话助手。企业知识、工作方法、任务过程和成果由企业掌握；智能体以专职、可审计、可控制的程序形态协同完成工作。

第一期只建设两类独立存在：

- **中台（控制平面）**：登记、审核、发现、选择、编排、调度、验收、恢复和审计智能体工作。
- **智能体群（执行平面）**：每个智能体是可独立部署、按任务拉起和停止的专业程序，在本机工作目录中调用本地工具、企业服务和 AI 运行时。

后续的微信、邮件、飞书、业务系统等接入层不在第一期实现。它们今后只需把标准化需求信号投递到中台；第一期通过模拟任务提交接口验证完整闭环。企业已有 RAGFlow 知识库是第一期真实知识源，知识查询智能体直接调用其 HTTP API。

## 2. 已确认的产品决策

1. 219 服务器是第一期唯一运行节点。项目代码、文档、数据均放在 `/home/middleground`。
2. 智能体是独立服务程序，不是中台内置函数；中台可按任务拉起、停止、重启其运行实例。
3. 智能体包放入智能体仓库后应自动发现、读取能力说明并申请登记；人工可先审核再启用，也可按策略允许可信来源自动启用。
4. 所有智能体共用一个不受限的 Linux 系统账号；每次任务有独立工作目录。只有中台显式声明协作关系的任务才共享同一工作目录。
5. 每个任务在启动时选择验收模式：`platform_auto`（中台评估）或 `human_review`（人工审核）。
6. PostgreSQL 使用 Docker 部署，持久化数据留在 `/home/middleground/data`。
7. Codex CLI 已安装并在 219 服务器登录；Codex 是首个运行时，但不是平台唯一运行时。
8. 第一期仅有一位管理员，以固定管理令牌访问提交、查询、审批和管理 API；令牌只以环境变量中的哈希/密文配置，绝不写入仓库、日志或任务事件。
9. 中台、节点管理服务和智能体实例均以当前已登录 Codex 的 `root` 账号运行。第一期接受该账号不构成隔离边界的风险。
10. Codex 智能体可调用本地 Shell、访问网络，并读写任务工作目录外的文件；第一期不增加运行时逐动作人工确认，仍保留任务级取消、验收和完整审计。
11. 未审核包只能被静态读取并登记为 `pending_review`，不执行探测代码；审核通过后才首次运行自检。
12. AI 根据任意自然语言需求生成执行图是中台核心能力，不限于预置任务模板。生成的图仍必须经过编译器、能力目录和策略校验后才可调度。
13. 自动验收只检查结果 Schema、必要产物/来源和未解决风险；无法确定质量时转人工。人工驳回后不自动重试，管理员须显式创建重试或新任务。
14. RAGFlow 服务地址作为 `RAGFLOW_BASE_URL` 配置；访问密钥仅以 219 服务器的根用户私有环境文件中的 `RAGFLOW_API_KEY` 保存，严禁进入 Git、文档、日志、任务事件或智能体提示词。

## 3. 目标、非目标与失败标准

### 目标

- 建立智能体包的发现、注册、审核、启用、停用与版本管理。
- 用统一且语言无关的契约管理中台与智能体之间的任务、进度、结果、错误和控制指令。
- 由中台 AI 把任意自然语言需求规划并编译为可持久化的任务执行图，并可靠恢复中断任务。
- 让第一个专业智能体通过 Codex 本地运行时完成实际任务，并以结构化结果返回中台。
- 对任务、智能体、运行时和审批形成可追溯审计记录。

### 非目标

- 第一期开通微信、邮件、飞书、业务系统连接器。
- 第一期开通企业记忆、人员/财务等数据源；仅预留适配器与模拟数据。RAGFlow 知识库除外。
- 第一期开通多服务器调度、高可用、多租户、SSO 或细粒度操作系统沙箱。
- 第一期开通通用低代码工作流编辑器或完整运营 UI。
- 第一期开通任意第三方智能体的无审查自动执行权，或让未审核包执行探测代码。

### 失败标准

- 中台直接依赖某一智能体的私有实现，导致新增或替换智能体需要修改中台业务代码。
- 任务在服务器或进程中断后无法知道已执行到哪一步，或重试会重复进行有副作用的操作。
- 未审核智能体能执行企业任务，或无法追溯谁、何时、用什么运行时完成了何种动作。
- 把 Codex 专有会话格式扩散为中台的公共协议，造成以后无法接入 Pi 等运行时。

## 4. 总体架构

```text
模拟需求提交 / 未来接入层
          │ TaskEnvelope v1
          ▼
┌─────────────────────────── 中台（控制平面）───────────────────────────┐
│ API 与会话 │ 策略/审批 │ 智能体目录 │ 规划编排 │ 调度恢复 │ 结果验收 │
│                     PostgreSQL：状态、事件、审计、检查点             │
└─────────────────────────────┬───────────────────────────────────────┘
                              │ 本机控制协议
                              ▼
┌──────────────────────── 节点管理服务 ────────────────────────────────┐
│ 智能体包发现 │ 进程生命周期 │ 工作目录 │ 心跳 │ 主机/运行时状态      │
└──────────────┬──────────────────────────────────────────────────────┘
               │ 按任务拉起/停止
               ▼
┌──────────────────────── 智能体群（执行平面）─────────────────────────┐
│ 知识查询智能体 │ 文档编写智能体 │ ……                                  │
│       统一 Agent Protocol v1 + 各自 Runtime Adapter                  │
│                 └─ Codex app-server / Codex exec / Pi / …            │
└─────────────────────────────────────────────────────────────────────┘
```

中台与智能体群是进程、职责和部署单元均分离的系统。中台拥有任务真相、策略和调度权；智能体拥有专业执行逻辑，不能自行改变任务终态、审批结论或其他智能体的权限。

## 5. 技术路线

### 5.1 选择

- **中台**：TypeScript、Node.js、NestJS，模块化单体部署。
- **首批智能体**：TypeScript、Node.js；协议以 JSON Schema 定义，后续可由 Python、Go 等语言实现。
- **数据库**：PostgreSQL，Docker Compose 部署，使用绑定目录 `/home/middleground/data/postgres`。
- **进程管理**：节点管理服务负责启动和监督智能体实例；第一期用 systemd transient service 管理任务进程。中台不直接执行任意 shell 指令。
- **通信**：控制与任务协议使用本机 HTTP/JSON；智能体以 HTTP 回调持续上报事件。所有请求和事件带版本号、任务 ID、实例 ID、幂等键和关联 ID。
- **可靠性**：PostgreSQL 是第一期唯一持久化真相来源。使用任务事件表、检查点、租约和恢复扫描器，而非一开始引入独立消息队列或工作流引擎。

### 5.2 采用此路线的理由

TypeScript 可同时实现中台、节点服务、智能体包工具和 Codex 适配器，首期迭代快。NestJS 提供适合企业控制平面的模块、验证、依赖边界与测试结构。模块化单体避免在尚无真实负载时把注册、编排、审批拆成难以调试的微服务；所有模块仍以独立接口和数据所有权设计，未来可拆分。

PostgreSQL 事件账本优先于消息队列：第一期规模只有一台服务器，任务状态、审计和恢复必须强一致且易于人工检查。待并发量、跨节点调度或外部事件吞吐验证后，再通过 Outbox 引入 NATS/JetStream；这不改变公共 Agent Protocol。

## 7. 智能体包与生命周期

### 7.1 智能体包

每个可安装智能体是 `/home/middleground/agents/<agent-id>/<version>/` 下的独立包，至少含：

```text
agent.yaml              # AgentManifest v1
dist/ or src/           # 专业执行程序
prompts/                # 经版本控制的工作方法
adapters/               # 可选的运行时适配器
schemas/                # 输入、输出与产物 JSON Schema
tests/                  # 健康与契约自检
```

`AgentManifest v1` 至少声明：稳定 ID、版本、发布者、能力列表、输入/输出 Schema、支持的运行时 Profile、权限请求、网络/文件需求、最大执行时长、资源提示、入口命令、健康检查、探测命令和默认验收建议。

### 7.2 两条独立生命周期

**智能体包（长期）：**

`discovered → pending_review → self_checking → ready → disabled / quarantined / retired`

包进入仓库后，节点管理服务只读取静态声明并登记为 `pending_review`，不启动其中任何代码。管理员批准后，节点管理服务以目标 `root` 账号首次运行其自检；只有自检成功才可进入 `ready` 并被中台编排。第一期审计采用应用层只追加事件记录，不承诺抵抗拥有数据库或主机最高权限者的篡改；后续再引入哈希链、外部归档或独立审计存储。

**智能体实例（单次任务）：**

`planned → leased → starting → running → waiting_approval → completing → accepted → stopped`

失败分支为 `interrupted`、`retrying`、`failed`、`cancelled`。每次实例都有唯一 `instance_id`、任务令牌、工作目录和运行时会话。实例完成后进程停止；其事件、产物索引和工作目录按保留策略保存。

## 8. Agent Protocol v1

公共协议不暴露 Codex、Pi 或任一语言的私有对象。传输初期采用 HTTP/JSON；Schema 使用 JSON Schema，版本以 `v1` 固定在路径和包体内。

管理员 API 统一使用 `Authorization: Bearer <fixed-token>`。第一期只有该管理员可提交任务、查询任务、批准智能体、审批结果、取消任务和创建重试；智能体不能调用管理员 API。令牌验证采用服务启动时从环境变量读取的哈希值，审计事件只记录令牌主体 `bootstrap-admin`，不记录原始令牌。

核心对象：

- **TaskEnvelope**：`task_id`、`session_id`、发起者、验收模式、目标、输入、上下文引用、工作目录规则、期限、幂等键、允许的运行时 Profile。
- **TaskPlan**：版本化 DAG。节点类型为 `agent_call`、`condition`、`approval`、`end`；每个节点具有输入映射、超时、重试与补偿策略。
- **AgentEvent**：`task_id`、`node_id`、`instance_id`、事件序号、时间、状态、进度、消息、检查点引用、运行时事件摘要和关联 ID。
- **AgentResult**：结构化输出、产物清单、证据/来源、质量自评、风险、建议后续动作、可重放的幂等键。
- **ControlCommand**：`start`、`pause`、`resume`、`cancel`、`stop`。命令与确认均写审计记录。

中台只认可信签名/令牌的回调，并拒绝过期租约或旧实例提交的事件。智能体不得直接把任务标为 `accepted`。

## 9. 编排、持久化与恢复

1. 中台收到模拟需求后创建 TaskEnvelope、验收模式与审计记录。
2. 中台规划智能体将任意自然语言需求、可用能力目录和策略上下文生成 `TaskPlanDraft`。首期规划智能体使用 `codex-app-server` Runtime Profile；具体模型由该 Profile 的部署配置决定，而不进入公共协议。
3. 计划编译器只接受符合 TaskPlan Schema 的图，并验证节点类型、输入输出 Schema、能力可用性、权限、运行时和工作目录共享规则，随后冻结一个计划版本。规划智能体不能直接执行计划、调用 Shell 或绕过策略。
4. 调度器为可运行节点申请数据库租约，选择 `ready` 的智能体版本，交由节点管理服务拉起实例。
5. 实例按序提交 AgentEvent；每个可恢复步骤同时产生中台检查点和智能体工作目录中的本地检查点。
6. 实例返回 AgentResult 后，中台运行结果校验。若任务为 `platform_auto`，只验证 Schema、必要产物/来源和未解决风险；不确定时转人工。若任务为 `human_review`，直接进入人工队列。人工驳回不会自动重试。
7. 所有节点终态满足后，任务才完成，节点管理服务停止实例。

恢复规则：

- 调度器定期扫描过期租约、超时心跳和 `interrupted` 实例。
- 恢复者从最近的**已确认检查点**创建新尝试，不复制已成功节点。
- 外部副作用必须携带 `task_id + node_id + attempt` 组成的幂等键；不具备幂等性的动作只能经人工审批节点。
- 运行时会话标识、任务输入、事件位置与产物索引保存于 PostgreSQL。恢复时由对应运行时适配器决定恢复会话或从可重复检查点重启。

## 10. 运行时适配层与 Codex

每个智能体调用抽象 `RuntimeAdapter`，而不是直接绑定某个 CLI：

```text
preflight(profile) → start(run context) → stream events → checkpoint/resume → cancel → collect result
```

运行时 Profile 由任务允许范围、智能体声明、策略和节点运行时状态共同解析。中台下发选中的 Profile，智能体再加载对应适配器；切换 `codex-app-server`、`codex-exec`、`pi` 不改变 TaskEnvelope、AgentEvent 或 AgentResult。

**首个实现：`codex-app-server`。** 智能体实例在自己的工作目录中拉起本地 app-server 子进程，通过标准输入输出的 RPC 协议初始化线程、启动回合、接收流式事件、处理运行时审批，并将其归一化为 AgentEvent。任务的 Codex 线程标识与运行时检查点由适配器记录。app-server 适合需要持续会话、流式进度、中断与审批的产品任务；`codex exec` 只作为有边界的短任务备选。

这一选择符合 OpenAI 对 app-server 的定位：应用可创建线程、启动回合、接收事件和处理审批，而产品仍拥有业务上下文、工具和控制边界。参考：[Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)。

## 11. 数据模型与目录

PostgreSQL 的核心表：`agents`、`agent_versions`、`agent_approvals`、`capabilities`、`nodes`、`tasks`、`task_plans`、`task_nodes`、`task_attempts`、`task_events`、`task_checkpoints`、`runtime_sessions`、`approval_requests`、`results`、`artifacts`、`workspace_leases`、`audit_events`。

大文件和可执行产物存文件系统，数据库只保存校验值、路径、类型、产生者与生命周期元数据。

```text
/home/middleground/
  control-plane/              # NestJS 中台代码
  node-manager/               # 单机节点管理服务
  agents/                     # 经审核前后的智能体包仓库
  shared/agent-protocol/      # JSON Schema 与 TypeScript 契约
  infra/                      # Docker Compose、systemd 与部署配置
  docs/                       # 设计、运行手册、协议说明
  data/
    postgres/                 # PostgreSQL Docker 绑定卷
    workspaces/<task-id>/     # 默认任务工作目录
    artifacts/<task-id>/      # 任务产物
    logs/                     # 结构化日志（非审计真相）
```

共享工作目录必须由计划节点显式声明 `workspace_mode: shared` 与共享组；默认是 `private`。

## 12. 第一阶段验收闭环

模拟任务：“依据 RAGFlow 中的客户资料，生成宣传文案并提交审核”。

本闭环冻结两个演示智能体的契约：

- **资料检索智能体**以只读方式调用 RAGFlow `POST /api/v1/retrieval`。它以 `question` 和配置的数据集 ID 列表请求数据，映射响应的 chunk `id`、`dataset_id`、`document_id`、`document_keyword`、`content` 与 `similarity` 为 `evidence[]`；每项含 `source_id`、`dataset_id`、`document_id`、`title`、`excerpt`、`relevance` 和 `source_path`。`RAGFLOW_DATASET_IDS` 可选；未设置时启动时列举当前密钥可见的数据集并使用其 ID。
- **文案编写智能体**接收 `evidence[]`，通过 Codex 生成 `copy.json` 与 `copy.md`。`copy.json` 至少含 `title`、`body`、`claims[]`、`source_ids[]`、`risk_notes[]` 和 `status`，其中每个可核验主张必须引用 `source_ids`。

资料检索智能体仅执行 RAGFlow 的只读数据集发现与检索调用；该演示任务只在其工作目录内创建产物，不调用业务系统、发送消息或修改企业外部数据。Codex 的网络访问仅用于其运行时本身；任何未来的外部写入能力均应作为明确智能体能力和人工审批节点另行设计。RAGFlow API 的请求和返回按其标准 `Authorization: Bearer` 认证与业务 `code` 字段判定，不能仅以 HTTP 200 判断成功。

1. 将“资料检索”和“文案编写”两个智能体包放入仓库，自动发现并进入待审核。
2. 管理员批准两个包后，中台能力目录可查询到它们。
3. 提交模拟需求。中台生成 `检索 → 文案编写 → 验收` 的计划，并拉起相应实例。
4. 文案智能体使用 Codex app-server，在该任务工作目录中生成结构化文案与产物。
5. 中台实时显示进度、运行时事件、产物和审计记录；任务按创建时的自动/人工验收策略结束。
6. 在智能体运行中终止其进程或重启中台。恢复器从最近检查点继续，且不重复已完成的检索或已写入的外部动作。
7. 任务完成后智能体实例停止，工作目录与所有证据可查询。

## 13. 风险与约束

- 共享且不受限的系统账号不是安全边界。第一期通过中台策略、工作目录登记、审核和审计降低误操作风险；后续可按需升级为独立账号、容器或沙箱。
- 目前 Codex CLI 的登录态必须对实际执行智能体的共享 Linux 账号可用。部署前需确认该账号与 Codex 登录态的归属。
- 一台服务器是单点故障；第一期依靠恢复而不是高可用，跨主机调度留到后续阶段。
- AI 自动规划只能产出受限 TaskPlan，任何计划均需编译器校验；它不能绕过权限或直接执行任意命令。
